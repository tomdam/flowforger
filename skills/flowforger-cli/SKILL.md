# FlowForger CLI Operations

## Overview

`flowforger` is a self-contained CLI for Power Automate / Logic Apps workflows: pull flows from Dataverse as TypeScript DSL (`.ff.ts`), edit, compile, run locally, and push back. **No npm packages are needed in the consuming project** — `.ff.ts` files are transformed by the CLI itself, never by `tsc`, and imports in them are dead weight (omit them).

Run `flowforger --help` for full flag reference. This skill covers what `--help` does not.

## Command Quick Reference

| Task | Command |
|------|---------|
| First-time project setup | `flowforger init --url <envUrl> --client-id <appId>` |
| Which Entra permissions a flow / the app registration needs | `flowforger scopes <flow.ff.ts>` / `flowforger scopes --all` |
| Pull one flow | `flowforger pull --name "My Flow" --auth` |
| Pull a whole solution | `flowforger pull --solution <UniqueName> --auth --out ./flows` |
| Push a flow back (updates or creates) | `flowforger push --file flow.ff.ts --auth` |
| Compare the local file with the live flow (what push would change) | `flowforger diff --file flow.ff.ts --auth` (exit 1 when they differ) |
| Run with an action's outputs replaced by a file | `flowforger run flow.ff.ts --mock Get_items=items.json` |
| Dry run: writes mocked, reads live, nothing else may call out | `flowforger run flow.ff.ts --mocks mocks.json --live Get_items --json` — see [Dry run](#dry-run-mock-the-writes-allow-the-reads) |
| Replay a cloud run locally (its trigger body, its recorded outputs pinned) | `flowforger run flow.ff.ts --auth --replay-run <runId> --json` — see [Replay a cloud run](#replay-a-cloud-run) |
| List a flow's cloud runs / inspect one | `flowforger runs --file flow.ff.ts --auth` / `flowforger run-show --run <runId> --file flow.ff.ts --auth` |
| Create a brand-new flow in a solution | `flowforger push --file flow.ff.ts --solution <UniqueName> --auth` |
| Activate / deactivate | `flowforger activate --id <guid> --auth --state 1 --status 2` (or `--url <envUrl> --token <t>`) |
| Logic Apps JSON → DSL | `flowforger generate-dsl --in clientdata.json --out flow.ff.ts --name MyFlow` |
| DSL → Logic Apps JSON | `flowforger compile flow.ff.ts --out clientdata.json --emit logicapps` |
| Validate (either format) | `flowforger validate <file.json\|file.ff.ts>` |
| Run locally (**live** — connector writes really happen, see Behavior Facts) | `flowforger run flow.ff.ts --in payload.json [--auth\|--sp-token …]` |
| Install/refresh these skills in a project | `flowforger skills install` (fetches latest from GitHub; `--bundled` for offline) |

## First-Time Setup (per project)

1. You need an **Azure AD app registration client ID** (delegated permissions; Dynamics CRM `user_impersonation` for Dataverse; SharePoint `AllSites.*` if flows use SharePoint). Ask the user for it — it is not discoverable.
2. In the project root: `flowforger init --url https://<org>.crm4.dynamics.com --client-id <appId>`. This auto-discovers the tenant ID, prompts a **device-code login**, discovers the environment's connection references, and writes `flowforger.config.json` to the cwd. Offline/no-credentials: add `--skip-discovery` (leaves connection reference names empty — fill before push of new flows).
3. Tokens are cached in `~/.flowforger/token-cache.json` (~90-day refresh); subsequent `--auth` runs are silent.

**Never hand-write `flowforger.config.json`** — generate it with `init`. Structure: `auth` (clientId, tenantId, `resources.dataverse`/`resources.sharepoint`), `global.connections` (connector → connection reference), `global.parser` / `global.generator` (codegen tuning), `environments.<name>` (overrides selected via `--config-env`).

**Config auto-loading:** `pull`, `push`, and every `--auth` path read `flowforger.config.json` from the **cwd** automatically. `generate-dsl`, `parity`, `compile`, and `optimize` use the config **only with an explicit `--config` flag**. CLI flags always override config values.

## Auth & Token Matrix

| Purpose | Flag / env | Token audience (resource) | Quick recipe |
|---------|-----------|---------------------------|--------------|
| Dataverse (pull/push/activate) | `--token` or `DATAVERSE_TOKEN` | the environment URL, e.g. `https://org.crm4.dynamics.com` | `az account get-access-token --resource <envUrl> --query accessToken -o tsv` |
| Anything, hands-free | `--auth` | (acquired per connector automatically) | needs `auth` section in config; device-code on first run |
| SharePoint connector (run) | `--sp-token` | `https://<tenant>.sharepoint.com` — **NOT Graph** | `az account get-access-token --resource https://<tenant>.sharepoint.com ...` |
| Office365/Excel/Word/OneDrive (run) | `--graph-token` etc. | `https://graph.microsoft.com` | `az account get-access-token --resource https://graph.microsoft.com ...` |

- **The SharePoint trap:** a Graph token with `Sites.Read.All` gives 401 against the SharePoint REST API. The audience must be the tenant's SharePoint host. Verify at jwt.ms: `aud` should contain `00000003-0000-0ff1-ce00-000000000000`.
- `activate` supports `--auth` from CLI > 0.4.0 (0.4.0 and earlier need `--token`/`DATAVERSE_TOKEN` explicitly). State values: activate = `--state 1 --status 2`; draft = `--state 0 --status 1`. `push` keeps the flow's state, so after a trigger change on an active flow, deactivate + activate so the trigger's webhook is re-registered.
- Explicit `--xxx-token` flags override `--auth` per connector.

## Behavior Facts (verified, not guessable from --help)

- **`compile` emits Flow IR by default.** For Power Automate `clientdata.json` you MUST pass `--emit logicapps` (and `--config` if connection references matter).
- **`run` is a live run, never a dry run.** With `--auth` or a token, every connector call goes to the real environment: a loop that updates rows updates them. There is no read-only flag and plain `run` has no record/replay. **To test up to a write safely, pass `--stop-before <ActionName>`**: the run executes everything before that action (reads included, live), then ends before it with the trace so far and the exact inputs the action would have been invoked with (connector params, HTTP request, child-flow body), exit code 3 (0 succeeded, 1 failed/cancelled). In JSON mode the result has `status: "Cancelled"`, `stopped: true` and `stoppedBefore: { nodeId, name, inputs }`. The action name must exist in the root flow (not a child flow); a name that is never reached prints a `[WARN]` and the flow runs to the end. No token is needed for the connector of the stopped action. For stepping, breakpoints at several places or inspecting variables, use the debugger instead: `flowforger mcp --auth` exposes a debug session as MCP tools (`debug_start`, `debug_set_breakpoints` — entries are `{action}`, `{line}` or `{nodeId}` — `debug_step`, `debug_get_variables`, `debug_evaluate`, `debug_stop`, …): set a breakpoint on the write action, inspect its inputs, stop. The MCP session records connector responses to `~/.flowforger/cassettes/` and replays them on the next start of the same flow (misses go live), capped per session by `--budget` (default 200). Register once with `claude mcp add flowforger -- flowforger mcp --auth`; the server cannot show a device-code prompt, so warm the token cache first with any `--auth` command in a terminal (e.g. `flowforger pull`). What a local run does and does not emulate: loop iterations run one at a time (the cloud runs 20 in parallel unless `repetitions:1` — `DSL047` warns), `paginationPolicy` IS applied for SharePoint and Dataverse (see the DSL skill, "Pagination"), and the cloud's connector quirks are measured by `conformance/` — so debug locally first, then do one cloud run as the final check for concurrency effects.
- **`run` output & exit code:** 0 only when the flow run `Succeeded`, 1 for anything else (Failed, Cancelled). When stdout is piped (the normal case for agents/CI) the JSON trace prints to **stdout** (jq-safe) and the human `=== FLOW FAILED ===` banner goes to stderr. On an interactive terminal a human-readable trace prints instead — pass `--json` to force the JSON trace (`--pretty` forces the opposite). The most explicit CI gate is still `.status == "Succeeded"` from the JSON. **JSON shape** (parse it rather than the pretty trace): top level `{ status, trace, artifacts }` with `status` one of `Succeeded`/`Failed`/`Cancelled`; `trace` is an array of nodes `{ nodeId, name, status, inputs?, outputs?, error?, children?, iterations? }` in execution order, the first being the trigger. Per node, `status` is `Succeeded`/`Failed`/`Skipped`/`Cancelled`; `outputs` is the action's full outputs (a connector or HTTP action: `{ statusCode, body }`, so a field is `.outputs.body.<field>`; a Compose: the value itself) and is **absent** on a Skipped node and on a call that failed without a response; `inputs` is the resolved payload the action was invoked with (connector, HTTP and child-flow calls only, also on failures); `error` is present on failed nodes (`{ name, code?, message? }`). A Condition's outputs are `{ conditionResult, branchTaken }` (`branchTaken` = `actions`/`elseActions`), a Switch's `{ matched, matchedCase, value }`, a foreach's `{ itemCount }`. If/switch/scope nodes hold their body under `children` (untaken-branch children appear as Skipped); a loop holds `iterations: [{ index, item, status, actions }]`. The engine's `[LOG]` lines (every REST request and response) go to stderr in JSON mode.
- **`run` logs resolved environment variables to stderr** (`[INFO] Env var 'x' = ...`) when a Dataverse connection is available. Values of Secret-typed variables and of names containing key/secret/password/token/credential are printed as `[redacted]`; `--verbose` shows them. Keep stderr out of transcripts anyway when a flow handles credentials in plain String variables with other names.
- **Un-awaited `ctx.*` action calls are SILENTLY OMITTED from the compiled flow** — no error at compile or run time, the action just doesn't exist. Always `await` action calls, and run `flowforger validate <file.ff.ts>` (diagnostic DSL017 catches this; exits 1 on DSL errors).
- **`pull --solution` matches the solution UNIQUE name**, not the display name. Find it in the maker portal (Solutions list, "Name" column) — there is no CLI command to list solutions.
- **Pulled `.ff.ts` embeds `workflowId`** in `@Flow({...})`, so `push --file <file> --auth` needs no `--id`. JSON carries no workflowId and no flow name, so JSON pushes need `--id` (or `--name` to look up / create by name).
- **`push` creates the flow when it does not exist yet.** Resolution order: `--id` → decorator `workflowId` → lookup by flow name. A name match is PATCHed; no match creates the flow. `--create` forces creation (errors if an id is also available); `--no-create` makes a miss an error — **use `--no-create` in CI**, where an accidental create is worse than a failure. `--solution <uniqueName>` places a newly created flow; it is ignored (with a warning) when updating.
- **`push` prints the flow's state after every push** (`State: Activated (...)` or `State: Draft (...) — not running! Activate: flowforger activate --id ...`), because a push keeps whatever state the record has and a flow pushed as Draft stays off until someone activates it. In CI add `--require-active` to exit 1 when the flow is not Activated after the push (a create always fails this check, after stamping the GUID).
- **`diff` shows what a push would change, per action.** `flowforger diff --file flow.ff.ts --auth [--id <guid> | --name <flow>]` resolves the live flow like `push` (id → decorator `workflowId` → name; an ambiguous name is refused), compiles the file as `push` would, and reports every action as `only local` (+), `only live` (−) or `changed` (~, with the kinds: type, inputs, expression, runAfter, moved) with each differing property as `live → local`, plus trigger, parameter and flow-description differences. Cosmetic differences are ignored (metadata ids, key order, expression whitespace, `item/field` vs nested keys, CRLF); connection references are compared by key only, a value difference is listed but not counted. Exit code 0 identical, 1 differences, 2 usage/resolution error. Piped output is JSON (`{ workflowId, flowName, file, identical, summary, actions, triggers, parameters, flow, connectionReferences }`); `--json`/`--pretty` force either. Run it before a push onto a flow others may have edited in the designer, and after a push to confirm the cloud holds what you sent.
- **`push --expect-clean` refuses to overwrite designer edits it can detect.** It diffs first and fails (exit 2, nothing patched) when the live flow has actions, triggers or parameters the local file lacks. A changed action cannot be told from a local edit, so it is not checked — use `diff` for the full picture. A create (no live flow) always passes.
- **`runs` and `run-show` read cloud run history.** `flowforger runs --file flow.ff.ts --auth [--top 20] [--status Failed]` lists the flow's cloud runs newest first (`runId`, status, start/end, error); `flowforger run-show --run <runId> --file flow.ff.ts --auth` prints one run in the **same shape as `run --json`** — `{ runId, status, startTime, endTime, error?, trace }`, `trace` entries `{ nodeId, name, status, inputs?, outputs?, error?, children?, iterations? }` — so the same jq paths work for a local and a cloud run; on a terminal it prints the same pretty trace as `run`. The values are the cloud's: a connector action's `inputs` are `{ host, parameters }` (locally they are the parameters alone), a trigger's `outputs` are `{ headers, body }`, a Skipped action carries its `code` (`ActionSkipped`, `ActionBranchingConditionNotSatisfied`). `--file`/`--id`/`--name` resolve the flow like `push`; the environment is found from the config's Dataverse URL (`--environment-id <guid>` overrides). Needs the flow-service token `--auth` acquires (the app registration's Power Automate `User` permission); `--flow-token` takes one directly. `run-show` exits 0 when the run Succeeded, 1 otherwise. Compare a failed cloud run with a local `run --json` of the same input to see where they diverge.
- **`run --mock <Action>=<file.json>` replaces an action's outputs** (repeatable). The action does not run and needs no token; its inputs are still resolved and shown; later expressions read the file's JSON. The value is used as is, so for a connector/HTTP/child-flow action the file is the full `{ "statusCode": 200, "body": { ... } }` shape (`body('X')` reads `.body`); a Compose mock is the value itself. The trace entry carries `mocked: true` (`(mocked)` in the pretty trace); a mock whose action is never reached prints a `[WARN]`; a mocked scope/loop is replaced whole. `--mocks mocks.json` takes one JSON object `{ "<Action>": <outputs>, ... }` instead of a file per action. Use them to run the rest of a flow against a known response (an empty list, an error body) without touching the environment.
- **`run --live <Action>[,<Action>]` is deny-by-default for calls that leave the machine.** With it, every connector, HTTP and child-flow action must be either mocked or listed as live; the first one that is neither ends the run before it executes, prints the inputs it would have sent, and exits 3 (`stoppedBefore.reason` is `"live"` in the JSON; `"stop-before"` when `--stop-before` stopped the run, which takes precedence). A forgotten write therefore cannot slip through. `ctx.connectorWebhook()` (approvals) never calls out locally and is not guarded.
- **Unknown options are rejected** (exit 2, with a "did you mean" hint): `-o out/` (single dash) and typos like `--emmit` used to be silently ignored, so `compile ... -o Json/` wrote into the cwd. Options always take two dashes.
- **A created flow is Draft, and its GUID is written back into your `.ff.ts`.** `push` never activates — run `activate` afterwards. After a create, the new GUID is stamped into that file's `@Flow({...})` decorator so later pushes resolve by id instead of by name. If the decorator can't be edited (e.g. `@Flow(SOME_CONST)`), the create still succeeds and the CLI prints the GUID to add manually.
- **Name resolution has three real limits.** (1) Two flows sharing a name → `push` refuses and demands `--id`, rather than guessing which to overwrite. (2) Flows owned by others and not shared with you are invisible to the lookup, so a push creates a duplicate — the create message says when no flow was visible. (3) `push` sends only `clientdata`, never `name`, so renaming in `@Flow({...})` and pushing by name creates a duplicate instead of renaming; push by id after a rename.
- **`push` never publishes or changes solution membership of an existing flow.** `.ff.ts` inputs are compiled on the fly using the cwd config's connection references. With `--auth`, `--url` may be omitted — it comes from `auth.resources.dataverse` in the config (an explicit `--url` overrides it).
- **`operationMetadataId` stripping** comes from `global.parser.skipMetadataFields` (init writes `["operationMetadataId"]`). `pull` applies it automatically via the cwd config (CLI ≥ 0.1.1 — check with `flowforger --version`); one-off override: `--skip-metadata-fields operationMetadataId` (also valid on `pull`, despite being listed under generate-dsl/parity options).
- **`validate` is permissive** — it checks schema shape, not connection-reference correctness or referential integrity. `ok:true` does not guarantee an importable flow; use `parity` for round-trip confidence. It does catch the placement rules the cloud enforces on save/activate: `Response`/`Terminate` inside a foreach/until loop (`DSL037` for `.ff.ts`, `RESPONSE_NESTED`/`TERMINATE_NESTED` for JSON — the cloud error is "...has type 'Response' that could not be nested under an action of type 'foreach'"), `Response` without a request trigger (`DSL038` / `RESPONSE_TRIGGER`), `Response` in a parallel branch and nesting deeper than 8 (warnings). It also enforces the definition limits (80-char names, 500 actions, 25 switch cases, 250 variables, concurrency/retry/until/recurrence ranges — `DSL039`–`DSL046` for `.ff.ts`), warns about variables changed inside a `for...of` that runs in parallel in the cloud (`DSL047`), rejects reads of actions that are not on the reading action's `runAfter` path (`DSL048` / `EXPR_RUNAFTER_PATH`, `EXPR_SELF_REFERENCE` — the cloud error is "Action 'X' must either be in 'runAfter' path or within a scope action on the 'runAfter' path"), and, for JSON, name uniqueness, `runAfter` integrity, expression references and `connectionReferences` consistency. For `.ff.ts` files the IR validator runs after a clean DSL pass, so those warnings show up there too.
- **`pull --out` means two different things.** For a single flow (`--id`/`--name`) it is the **file path** to write (`--out flows/MyFlow.ff.ts`; the parent directory is created). For `--solution`/`--all` it is the **directory** to fill (created if missing), one `<FlowName>.ff.ts` per flow. Without `--out`, both write into the cwd.

## Dry run: mock the writes, allow the reads

There is no `--dry-run` flag. A dry run is `--mocks` for every action that would change something, `--live` for the reads you want real, and the JSON trace as the plan. You know the flow, so you decide what is a write and what a realistic answer looks like; `--live` makes sure nothing you missed executes.

1. **Classify the actions.** Writes: `ctx.connectors.*` operations whose id starts with `Create`, `Post`, `Patch`, `Update`, `Upsert`, `Delete`, `Send`, `Reply`, `Forward`, `Upload`, `Copy`, `Move`, `Add`, `Remove`, `Set`, `CheckIn`/`CheckOut`, `Perform…Action`/`…Function` (Dataverse actions — treat as writes unless you know the action is read-only), `HttpRequest` to SharePoint with a method other than GET, every `ctx.http()` with a method other than GET/HEAD, every `ctx.callWorkflow()` (the child may write), every `ctx.connectorWebhook()`. Reads: `Get…`, `List…`, `Search…`, `Find…`, `Download…`, GET requests. When unsure, mock it — a mocked read costs you nothing.
2. **Write `mocks.json`:** `{ "<ActionName>": <outputs>, ... }`. A connector, HTTP or child-flow mock is the **full outputs**, `{ "statusCode": …, "body": … }`, because `ctx.body('X')` reads `.body`: a create answers `201` with the row/item you sent plus the id later actions read (`ID` for SharePoint, `<entity>id` for Dataverse) in the shape the DSL skill's connectors.md documents; an update `200` with the row; a delete or a sent mail `{ "statusCode": 204 }` / `{ "statusCode": 200 }` with no body. A Compose mock is the value itself. Use recognisable fake ids (`00000000-0000-0000-0000-000000000001`) so they are easy to spot in the plan. **Mock any read that depends on an earlier write too** (a query for the row you just "created" finds nothing live) — that is the one thing no dry run can get right.
3. **Run:** `flowforger run flow.ff.ts --in payload.json --auth --mocks mocks.json --live Get_items,Get_user --json > dry-run.json`. Exit 0: the logic ran through. Exit 3 with `stoppedBefore.reason: "live"`: an action you did not classify would have called out — add it to `mocks.json` (a write) or to `--live` (a read) and run again. Exit 1: the flow failed; the trace says where.
4. **Read the plan:** every trace entry with `mocked: true` is a write that did not happen, and its `inputs` are exactly what the flow would have sent (connector parameters, the HTTP request, the child-flow body) — show those to the user. Check that every write you listed in step 1 appears mocked; `jq '[.. | objects | select(.mocked) | {name, inputs}]' dry-run.json` lists them.
5. **Variants:** keep one `mocks.json` per scenario (happy path, empty list, a `4xx` error body) next to the flow; `--stop-before X` with `--live` runs live up to a point; `flowforger mcp` with breakpoints when you need to inspect variables between steps.

### Replay a cloud run

When a run in the cloud is the scenario — a production failure to reproduce, a run whose data you want to step through — let the cloud write the mocks: `flowforger run flow.ff.ts --auth --replay-run <runId> --json` (run ids from `flowforger runs --file flow.ff.ts --auth`). The run's trigger outputs become the input (`--in` overrides), and every connector, HTTP and child-flow action the run recorded is pinned to the outputs the cloud recorded — per loop iteration, and a failed action fails locally with the cloud's code and error, so the catch path runs as it did — while Composes, variables and conditions recompute from those values. Safe mode is implied (`--live` with nothing listed): an external action the run has no pin for (an action you added, an extra loop iteration, a branch the run did not take) stops the run before it with its inputs, exit 3. `--live X` unpins X so it calls out for real; a `--mock X=…` wins over X's pin at every iteration (change one answer, keep the rest). The `[WARN]` lines name what could not be pinned: secure outputs (not downloadable) and actions the local file no longer has. The JSON result has `replayedRun: { runId, status }`, and every pinned entry carries `mocked: true` like a mock. Compare it with `flowforger run-show --run <runId>` when something recomputes differently: that is the local engine disagreeing with the cloud, which is worth reporting.

## Common Mistakes

| Mistake | Fix |
|---------|-----|
| Hand-writing `flowforger.config.json` from guessed field names | Always `flowforger init` (with `--skip-discovery` when offline) |
| `compile flow.ff.ts --out clientdata.json` without `--emit logicapps` | Output was IR; add the flag |
| Passing a Graph token as `--sp-token` | 401; acquire with SharePoint host as resource |
| Using the solution display name with `--solution` | Use the unique name |
| Forgetting `await` on a `ctx.*` call | Action silently vanishes from the flow; `flowforger validate` catches it |
| Expecting `push` to activate/publish | Follow with `flowforger activate` — a created flow is Draft |
| Pushing in CI without `--no-create` | A typo'd name silently creates a second flow instead of failing |
| Pushing over a flow someone edited in the designer | `flowforger diff --file flow.ff.ts --auth` first; `push --expect-clean` refuses when live has actions the file lacks |
| Renaming a flow in `@Flow({...})` then pushing by name | Creates a duplicate; `push` never updates `name`. Push by id |
| Adding `import` lines or npm deps for `.ff.ts` types | Not needed; the CLI resolves everything itself |

For authoring `.ff.ts` content (DSL rules, connectors, expressions), see the `flowforger` skill if installed alongside this one.
